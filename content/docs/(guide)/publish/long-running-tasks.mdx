title: Handle long-running tasks
description: Let a call take longer than 30 seconds, by doing the work on your server or in a queue worker, and reporting the result to Varis when it's ready.
---

Varis waits 30 seconds for your endpoint's first answer. If the work takes longer, your endpoint should tell Varis that the call has started, and sends the result when it's ready. The agent checks back with Varis at intervals until then.

The SDK does this for you. You add one line to your code, after the `varis.requests.verify` check. Requests that aren't from Varis, such as those from signed in users, pass through unchanged.

<Callout title="Not a TypeScript project?">
Report on long-running tasks by hand. For more information, see [Report on long-running tasks without an SDK](/sdks/other-languages#report-on-long-running-tasks-without-an-sdk).
</Callout>

## Before you begin

- Install `@usevaris/sdk` 1.2.0 or later.
- Verify requests with `varis.requests.verify`. For more information, see [Handle requests](/publish/handle-requests).

## How a long-running task works

1. Varis calls your endpoint, as it does for every call.
1. If your endpoint hasn't answered after 20 seconds, the SDK notifies Varis that the call has started.
1. While the work runs, the SDK notifies Varis every 30 seconds.
1. When the work ends, the SDK sends its answer to Varis. A `2xx` JSON answer is the result. Any other answer, or a thrown error, fails the call, and the agent isn't charged.

A long-running task fails, and the agent isn't charged, in any of these cases:

1. Varis doesn't receive a notification for 5 minutes. Varis infers that your server stopped.
1. The call hasn't finished 24 hours after it started. Every task gets a 24-hour deadline.
1. The result is larger than 4 MB of JSON, or doesn't match your output schema.

If the call ends first, for example at the 24-hour deadline, the SDK stops reporting on it and doesn't send a result. Your job isn't stopped or told to stop. It runs to the end.

## Choose where the work runs

| Where your code runs | What to use |
| --- | --- |
| Next.js on any host, any framework on Vercel, Netlify Functions, or Cloudflare Workers | [`handleOnServer`](#run-the-work-in-the-route). Nothing else to set. On Vercel, also export `maxDuration` from the route. |
| A server that keeps running, such as a virtual machine, a container, Railway, Fly, or Render | [`handleOnServer`](#run-the-work-in-the-route). Nothing else to set. |
| Any other serverless host | [`handleOnServer`](#run-the-work-in-the-route), with the host's `waitUntil` |
| AWS Lambda directly, or work that runs longer than your platform allows | [`delegateToWorker` and `handleInWorker`](#run-the-work-in-a-queue-worker) |

On AWS Lambda, `handleOnServer`'s background work stops as soon as the function returns, so use a queue worker. On any serverless platform, the work can't run longer than the platform's maximum duration. When the platform stops the function, the notifications stop, and the call fails 5 minutes later. For work that runs longer, use a queue worker.

## Run the work in the route

Wrap the route's existing work in `varis.requests.handleOnServer`. Pass the call itself, such as `renderVideo(request)`, not the function name `renderVideo`.

<Tabs items={['Next.js', 'Express']}>
<Tab value="Next.js">

```ts title="app/api/render/route.ts"
import { varis } from "@/lib/varis";

export const maxDuration = 300; // On Vercel: up to your plan's limit.

export async function POST(request: Request) {
  const isVaris = await varis.requests.verify(request);
  const isUser = await authoriseUser(request.headers.get("authorization"));
  if (!isUser && !isVaris) {
    return Response.json({ message: "Unauthorised" }, { status: 401 });
  }

  // Before Varis, this line was:
  // return renderVideo(request);

  // Now, this. The outcome is the same for signed in users.
  return varis.requests.handleOnServer(request, renderVideo(request));
}
```

Before Varis, the last line was `return renderVideo(request);`.

</Tab>
<Tab value="Express">

```ts title="routes/render.ts"
router.post("/render", async (req, res) => {
  const isVaris = await varis.requests.verify(req);
  const isUser = await authoriseUser(req.headers.authorization);
  if (!isUser && !isVaris) {
    return res.status(401).json({ message: "Unauthorised" });
  }

  // Before Varis, this line was:
  // return renderController(req, res);

  // Now, this. The outcome is the same for signed in users.
  return varis.requests.handleOnServer(req, renderController(req, res));
});
```

Before Varis, the last line was `return renderController(req, res);`. 

20 seconds after the task starts, the SDK notifies Varis that the task has started. Varis holds the line open, expecting a result. 

At intervals, the SDK notifies Varis on the status of the task. If Varis doesn't get this routine notification for 5 minutes, it infers that your server stopped, so it closes the transaction and the agent is not charged.

When your controller later calls `res.json`, the SDK sends that response to Varis as the outcome of the task. Once Varis receives this final outcome, it closes the transaction and the agent is charged.

</Tab>
</Tabs>

Replace `authoriseUser` with however your route checks its users today.

`handleOnServer` works like this:

- **For a request that isn't from Varis,** it returns the work's own answer, untouched.
- **If the work answers within 20 seconds,** it passes the answer to Varis unchanged, as without the SDK.
- **If the work takes longer,** it notifies Varis with `{"status": "started"}`, sends a notification every 30 seconds with `{"status": "running"}`, and sends the task's output to Varis when it's ready.
- **If the response has started streaming before 20 seconds,** it doesn't bother about a notification.

The process must keep running until the work ends. On the hosts in the first two rows of the table, the SDK takes care of this, and you don't set anything. On Vercel, also export `maxDuration`.

## Run the work in a queue worker

If your route already puts the work on a queue, add `varis.requests.delegateToWorker` to the job, and wrap the job in `varis.requests.handleInWorker` in the worker.

In the route, after the same `varis.requests.verify` and user check as in the previous section, add one field to the job you queue:

```ts title="routes/render.ts"
await queue.add("render", {
  input: req.body,
  varis: await varis.requests.delegateToWorker(req), // null for your own users
});

res.json({ queued: true }); // Unchanged. Varis ignores it.
```

`delegateToWorker` tells Varis that the call has started, and waits for Varis to confirm. It then returns the details that the worker needs to report on the call. For a request that isn't from Varis, it returns `null`.

In the worker, pass those details and your job to `handleInWorker`:

```ts title="workers/render.ts"
worker.process("render", (job) =>
  varis.requests.handleInWorker(job.data.varis, () => render(job.data.input)),
);
```

`handleInWorker` notifies Varis as soon as the job starts and every 30 seconds while it runs. It then sends the job's return output as final result, or fails the call if the job throws. It returns the value, or rethrows the error, so your worker behaves as it did before. With `null` or missing details, such as for a job your own users queued, it just runs the job like before.

Follow these rules:

- **Let `delegateToWorker` errors fail the route.** It throws when it can't reach Varis, or when the call has already ended. Don't queue the job because Varis refunds the call.
- **Call `delegateToWorker` within 30 seconds** of the request arriving.
- **Put the details in the queue message, never the request.** The details are plain JSON.
- **Start the job within 5 minutes.** A job that waits longer in the queue fails, because Varis stops waiting for a notification after 5 minutes.

## Results

A long-running task's result follows the same rules as any other:

- It must match your output schema.
- It must be 4 MB of JSON or less. For a larger result, return a URL to your own storage instead. The SDK fails a larger result, and the agent isn't charged.

Varis never sees the body of an answer that fails, or a thrown error.

## Limits

- **Keep the event loop free.** The SDK reports from a timer in the same process. Work that blocks the event loop for 5 minutes, such as a long, CPU-heavy loop, stops the reports, and the call fails. Run CPU-heavy work in a worker thread or another process.
- **Use `handleOnServer` with Web-style or Express-style work only.** Web-style work resolves to a `Response`, as in Next.js, Hono, Bun, and Deno. Express-style work writes to `res`. With Fastify, Koa, or another Node.js framework, use `delegateToWorker` and `handleInWorker`.
